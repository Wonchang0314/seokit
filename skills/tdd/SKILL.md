# TDD — 테스트 먼저

테스트를 먼저 쓰고, 실패하는 걸 보고, 통과할 만큼만 구현한다.
**실패하는 걸 직접 보지 않은 테스트는 맞는 걸 검사하는지 알 수 없다.**

## 철칙

```
실패하는 테스트 없이 제품 코드를 쓰지 않는다
```

테스트보다 코드를 먼저 썼다면 지우고 테스트부터 다시 한다. "참고용으로 남겨 두기"도 안 된다 — 결국 그 코드에 맞춘 테스트가 된다.

예외(사용자에게 먼저 확인): 버릴 프로토타입, 생성된 코드, 설정 파일.

## 순서

1. **RED — 실패하는 테스트 하나.** 동작 하나, 이름이 곧 기대 동작, 가능한 한 실제 코드(mock 은 불가피할 때만).
2. **실패 확인 (생략 금지).** 해당 테스트만 실행해 본다.
   - 오류(오타·import)가 아니라 **실패**여야 하고, 실패 메시지가 예상한 이유(기능 없음)여야 한다.
   - 바로 통과하면 이미 있는 동작을 검사하는 것 — 테스트를 고친다.
3. **GREEN — 통과할 최소 코드.** 테스트가 요구하지 않는 옵션·확장·주변 리팩터는 넣지 않는다.
4. **통과 확인 (생략 금지).** 그 테스트 + **프로젝트 전체 테스트**를 돌린다. 경고·오류 없는 출력이어야 한다.
   - 실패하면 테스트가 아니라 코드를 고친다.
   - 내 변경과 무관한 실패도 보고에 이름으로 적는다(본 걸 빼면 거짓 보고).
5. **REFACTOR — 초록일 때만.** 중복 제거·이름 정리·헬퍼 추출. 동작은 추가하지 않고, 계속 초록을 유지한다.
6. 다음 동작으로 반복.

## 버그 수정 예

```typescript
// RED: 버그를 재현하는 테스트
test('빈 이메일은 거부한다', async () => {
  const result = await submitForm({ email: '' });
  expect(result.error).toBe('Email required');
});
// 실행 → FAIL: expected 'Email required', got undefined  (예상한 이유로 실패)

// GREEN: 최소 수정
if (!data.email?.trim()) return { error: 'Email required' };
// 실행 → PASS, 전체 스위트도 PASS
```

버그는 항상 재현 테스트부터. 테스트가 수정을 증명하고 재발을 막는다.

## 멈춰야 할 신호

- 코드를 먼저 썼다 / 테스트를 "나중에" 붙이려 한다
- 테스트가 처음부터 통과했다 / 왜 실패했는지 설명 못 한다
- "이미 손으로 확인했다", "이번만 예외" 라는 생각이 든다

→ 코드를 지우고 RED 부터 다시.

## 막힐 때

| 문제 | 대응 |
|---|---|
| 어떻게 테스트할지 모름 | 쓰고 싶은 API 모양대로 단언부터 적는다. 그래도 모르면 사용자에게 묻는다 |
| 테스트가 복잡함 | 설계가 복잡하다는 신호 — 인터페이스를 단순화 |
| 전부 mock 해야 함 | 결합이 강하다는 신호 — 의존성 주입 |
| 준비 코드가 거대함 | 헬퍼로 빼고, 그래도 크면 설계를 단순화 |

## 완료 체크

- [ ] 새 함수·동작마다 테스트가 있다
- [ ] 각 테스트가 구현 전에 예상한 이유로 실패하는 걸 봤다
- [ ] 통과할 최소 코드만 썼다
- [ ] 전체 테스트 통과, 출력에 오류·경고 없음
- [ ] 경계값·오류 경로를 다뤘다
- [ ] writing-good-tests.md 의 「돌연변이 점검」을 했다

실행 명령(vitest·gradle 등)은 프로젝트 문서·스킬을 따른다.
