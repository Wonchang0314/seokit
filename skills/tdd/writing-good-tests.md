# 좋은 테스트 쓰기

테스트를 쓰거나 고칠 때, mock·테스트 헬퍼를 추가할 때 본다.

테스트는 특정한 고장을 잡으려고 존재한다. 원칙은 둘이다.

```
1. 모든 테스트는 자기가 잡는 고장을 말할 수 있어야 한다
2. 모든 테스트는 진짜 코드를 돌려야 한다
```

## 원칙 1 — 잡는 고장을 말하기

테스트 본문을 쓰기 전에 답한다: **제품 코드가 어떻게 바뀌면 이 테스트가 실패하나? 그 변화는 버그인가, 의도된 결정인가?**
잘못된 분기, 빠진 부수효과, 틀린 인자, 경계값, 깨진 계약을 잡을 때 테스트가 값을 한다.

- **기대값은 따로 구한다.** 리터럴이나 손으로 검산한 픽스처를 쓴다. 표 기반 테스트 + 리터럴 `want` 가 가장 좋다. 테스트 대상 코드(나 그 헬퍼)로 기대값을 만들면 무엇을 해도 통과한다.
  ```typescript
  // ❌ 같은 함수가 양쪽을 계산 — 항상 참
  expect(buildQuery({ tag: 'a' })).toBe(buildQuery({ tag: 'a' }));
  // ✅ 손으로 구한 리터럴
  expect(buildQuery({ tag: 'a' })).toBe('tag:"a"');
  ```
- **변경 감지기 금지.** 상수값·문구·내부 구조처럼 의도적 결정만 깨뜨릴 수 있는 테스트는 설계 변경 때마다 울리고 버그엔 잠잔다. `expect(MAX_RETRIES).toBe(5)` 대신 "실패하면 5번 재시도하고 6번째는 없다"를 검사한다.
- **텍스트 말고 동작.** 스크립트·설정 파일에 특정 줄이 있는지 grep 하지 않는다. 입력을 주고 실행해서 출력·부수효과·종료코드를 본다. 사람이 읽는 문서엔 테스트가 필요 없다.
- **내 코드의 경계만.** 내가 등록한 라우트, 내가 만드는 쿼리·페이로드를 검사한다. 프레임워크가 핸들러를 부르는지는 프레임워크의 테스트다. 생성자·getter·단순 전달은 검증·정규화·기본값·파생·부수효과가 있을 때만 테스트한다.

```
테스트 본문을 쓰기 전:
  이 테스트를 실패시킬 제품 코드 변화를 말한다.
    말 못 함            → 관찰 가능한 동작 기준으로 다시 설계
    "소스 문구가 바뀜"  → 실행해서 효과를 검사
    의도적 결정뿐       → 변경 감지기. 그 결정에 기대는 동작을 검사
  기대값이 테스트 대상 로직을 재사용하면 → 리터럴로 바꾼다
```

## 원칙 2 — 진짜 코드를 돌리기

- **mock 자체를 단언하지 않는다.** mock 이 있으면 통과, 없으면 실패하는 단언은 컴포넌트에 대해 아무것도 말하지 않는다. "지금 mock 의 동작을 테스트하고 있지 않나?"
  ```typescript
  expect(screen.getByRole('navigation')).toBeInTheDocument();   // ✅ 실제 동작
  expect(screen.getByTestId('sidebar-mock')).toBeInTheDocument(); // ❌ mock 존재 확인
  ```
- **적절한 층에서 mock.** 대체하기 전에 실제 메서드의 부수효과를 파악한다. 느리거나 외부인 부분만 mock 하고, 테스트가 기대는 부분은 진짜로 둔다. 모르겠으면 실제 구현으로 먼저 돌려 본다.
- **대역은 구체적으로.** 인자·호출 횟수·순서가 계약이면 단언한다. 무엇이든 받아 주는 가짜는 아무것도 검증하지 않는다. 성공·오류·잘못된 입력 분기마다 별도 픽스처를 둔다.
- **실제 데이터 구조를 통째로.** mock 응답은 테스트가 읽는 필드만이 아니라 실제 구조 전체를 흉내 낸다. 빠진 필드는 조용히 통합을 깨뜨린다.
- **제품 클래스엔 제품 메서드만.** 테스트에서만 쓰는 정리 코드(`destroy()` 등)는 테스트 유틸로 뺀다.
- **복잡한 mock 보다 실제 컴포넌트.** mock 준비가 테스트 본문보다 커지면 실제 컴포넌트로 통합 테스트를 쓴다. "여기서 mock 이 꼭 필요한가?"

## 돌연변이 점검

끝내기 전에 제품 코드를 머릿속으로 망가뜨려 본다. 현실적인 각 변형마다 테스트가 최소 하나는 실패해야 한다.

- 틀린 상수·인자 / 틀린 분기 처리
- 빠진 상태 변경·부수효과 / 빈 값·기본값 반환
- 0·빈 값·null·권한 없음·잘못된 입력에 대한 검증 누락

아무 테스트도 못 잡는 변형이 있으면 그 동작은 보호받지 못하고 있거나, 테스트가 동어반복이다.

## 경고 신호

- 준비와 단언이 같은 객체를 써서 같을 수밖에 없다
- 크래시·셀렉터 누락으로만 실패할 수 있다
- 의도적 변경엔 매번 깨지고 실수엔 안 깨진다
- 기대값이 루프·빌더·헬퍼 뒤에 숨어 있다
- 소스 텍스트를 grep 한다
- 커버리지 채우기용 — 확인하는 결과·부수효과가 없다
- `*-mock` testid 를 단언하거나, mock 을 빼면 실패한다
- 테스트 파일에서만 호출되는 제품 메서드가 있다
- "혹시 몰라서" mock 한다
