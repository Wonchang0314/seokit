# Explain Design (Notion)

## Overview

승인된 설계 변경을 사용자의 Notion에 **읽고 배울 수 있는 한 페이지**로 발행한다. 이는 superpowers spec 파일 + writing-plans plan 작성을 **대체**한다 — 산출물은 repo 문서가 아니라 Notion 페이지다. 페이지는 **이전→이후 delta**를 가르치고, 그 delta를 이해한 독자만 통과할 수 있는 퀴즈로 끝난다.

주 독자는 **미래의 사용자 본인**(복습·학습)이며, 팀원 리뷰에도 쓰인다. 그러니 "지금은 당연한" 맥락도 6개월 뒤의 내가 못 알아볼 수 있다고 가정하고 쓴다.

## 형제 스킬과의 경계 (혼동 방지)

| | **이 스킬 (explain-design-notion)** | **explain-diff-notion** |
|---|---|---|
| 시점 | 구현 **전** — 승인된 설계안 | 구현 **후** — 이미 커밋된 diff/PR/브랜치 |
| 척추 | 이전→이후 설계 대조 (delta) | 코드 변경 자체 훑기 |
| 대체 대상 | spec 파일 + writing-plans plan | 없음 (설명 자료 추가) |

**아직 코드가 없고 "이렇게 바꿀 거야"면 이 스킬. 이미 코드가 커밋됐고 "이렇게 바꿨어"면 explain-diff-notion.** 애매하면: 설명할 대상이 diff로 존재하는가? 존재하면 diff 스킬, 아니면 이 스킬.

## When to Use

- 설계/리팩터가 승인됐고 원래라면 spec + plan을 쓸 상황.
- 사용자가 그 설계를 자기 Notion에 남기길 원함 (Notion MCP 연결 있음).
- 독자가 목표 상태만이 아니라 **현재 설계에서 무엇이 바뀌는지**를 파악해야 함.

Not for: 이미 커밋된 diff (→ `explain-diff-notion`); repo에 두고 싶은 일상 spec.

## 실행 절차 (순서대로 — 건너뛰지 말 것)

정찰 → 확인 → 작성 → 발행. 각 단계는 앞 단계 산출물에 의존한다.

1. **부모 페이지 확정.** 기본값: 사용자의 "복습" 페이지 (page_id `394aabb1-2d08-80b9-8e68-d46964876ea2`). 다른 위치 지시가 없으면 이 기본값을 그대로 쓰되 "복습 페이지 아래에 만들게요"라고 한 줄 밝힌다. **워크스페이스 루트에는 절대 만들지 않는다.**
2. **Notion 마크다운 스펙 로드.** `notion://docs/enhanced-markdown-spec`를 ReadMcpResource로 읽는다. Notion-flavored 마크다운(`<callout>`, `<table>`, `<details>` 토글, ```mermaid)을 **반드시** 쓴다. 순수 `|`-테이블이나 `- [ ]` 체크박스는 냄새다.
3. **코드 정찰 — old 설계까지.** 주변 코드를 폭넓게 탐색해 **기존(old) 설계와 새(new) 설계 둘 다** 정확히 파악한다. old를 추측으로 쓰지 말 것 — delta 전체가 여기서 나온다. 파일/함수/수치를 실제로 확인한다(measure, don't guess).
4. **퀴즈 먼저 스케치.** 본문을 다 쓰고 퀴즈를 덧붙이면 delta 앵커가 약해진다. 3번에서 파악한 delta로 퀴즈 5문항 뼈대를 먼저 잡고, 본문이 그 답을 뒷받침하도록 쓴다.
5. **본문 작성 → 발행.** 아래 섹션 순서대로 쓰고 `notion-create-pages`로 발행, 페이지 URL을 사용자에게 반환한다.

## Required Page Sections (in order)

The page IS these sections. Omit none.

1. **배경 (Background)** — 초심자를 위한 기존 시스템 설명에서 시작해 이 변경이 건드리는 지점으로 좁힌다. *왜* 바꾸는지(동기/제약)를 `<callout>`으로.
2. **이전 → 이후 설계 (Old → New)** — 두 설계를 나란히: 각 축을 대조하는 `<table>` + before/after `mermaid` 다이어그램. **이게 척추다** — 이후 모든 섹션이 여기로 되돌아온다.
3. **직관 (Intuition)** — 핵심 아이디어를 장난감 데이터로: 새 설계의 동작을 보이는 구체적 워크드 예제(~5행 샘플). 다이어그램 권장.
4. **변경점 (Change points)** — 파일/모듈 × 무엇이 바뀌나(신규 / 수정)의 `<table>`.
5. **폐기 대상 (Deprecated / removed)** — 제거·은퇴되는 파일/함수 + 이유의 `<table>`. 무엇을 *유지*하며 왜 유지하는지도 밝힌다.
6. **사이드 이펙트 (Side effects)** — 동작/데이터/성능상 결과; 위험한 건 `<callout>`.
7. **다른 옵션 (Alternatives considered)** — 저울질 후 **기각한** 옵션들, 각각 why-not. 선택한 길의 tradeoff가 아니라 기각된 대안.
8. **퀴즈 (Quiz)** — 핵심. 아래 계약대로.

가능한 모든 주장을 실제 수치/파일에 근거한다(measure, don't guess).

## Quiz Contract (차별점 + 자가 학습)

정확히 **5문항**. 각 문항은 **새 설계가 기존과 어떻게 다른지 이해한 사람만** 답할 수 있어야 한다 — 일반 지식으로도, 새 상태만 알아도 못 푼다. old 설계를 몰라도 답할 수 있으면 다시 쓴다.

**난이도 배분** (복습 깊이 확보):
- 최소 **1문항은 쉬운 워밍업** — delta를 대충 읽어도 잡히는 기본 대조.
- 최소 **1문항은 깊은 문항** — 사이드이펙트(섹션 6)나 엣지케이스를 파고들어, 페이지를 정독한 사람만 통과.
- 나머지는 중간 난이도: 페이지를 공부한 독자는 통과, 스킴한 독자는 실패. 함정 문제는 없다.

**형식:**
- 각 문항을 delta에 앵커: "이전엔 X였는데 이제 Y — 왜 / 무엇이 깨지나 / 어떤 수가 바뀌나?"
- 객관식(3~4 보기). 각 보기는 `<details>` 토글이며 본문은 ✅ 또는 ❌로 시작하고 **왜인지** 설명한다(본문을 탭으로 들여써 중첩).
- 오답 중 최소 하나는 그럴듯한 **변경 전 가정** — 설계가 바뀌었기 때문에만 틀린 것.
- **되돌아가기 앵커 (복습 루프):** 각 문항 정답 해설 끝에, 이 문항을 틀렸다면 다시 봐야 할 상위 섹션을 가리킨다 — 예: `↩ 헷갈렸다면 §2 이전→이후 설계로 돌아가세요.` 주 독자가 미래의 본인이므로, 오답이 곧바로 복습 지점으로 연결되게 한다.

Example question:

**3. 기존엔 폐점 매장이 지도에 안 떴는데, 신규 설계에선 왜 프론트가 폐점을 직접 걸러야 하는가?**

<details>
<summary>보기 A — 신규 API가 폐점까지 원장으로 내려주기 때문</summary>
	✅ 레거시 WFS 뷰는 폐점을 원천 제외했지만 REST 원장은 폐점을 포함하므로, 이전과 같은 화면을 유지하려면 프론트가 걸러야 한다. ↩ 헷갈렸다면 §2 이전→이후 설계, §6 사이드 이펙트로 돌아가세요.
</details>
<details>
<summary>보기 B — 폐점은 원래도 소스에 있었고 필터 위치만 옮긴 것</summary>
	❌ 레거시 WFS엔 폐점이 없었다. 이 변화 자체가 프론트 방어가 새로 필요한 이유다.
</details>

## Publish

`notion-create-pages`로 확정된 부모 아래에, 주제를 담은 이모지 `icon`, 상단 근처에 `<table_of_contents/>`, 그리고 이 문서가 **구현 전 설계 문서**임을 표시하는 리드 `<callout>`(+ 측정 근거/날짜)을 넣어 발행한다. 페이지 URL을 사용자에게 반환한다.
